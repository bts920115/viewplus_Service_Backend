# ViewPlus | 관심사를 함께 경험하는 소셜 라이브 플랫폼

## 1. 프로젝트 소개

ViewPlus는 모바일 화면을 실시간으로 공유하고, 친구 또는 관심사가 비슷한 사용자가 같은 라이브 방에 참여해 콘텐츠를 함께 보며 대화할 수 있는 소셜 라이브 플랫폼입니다.

현대인은 YouTube, Instagram, X, Facebook, 커뮤니티 등 여러 플랫폼에서 콘텐츠를 소비합니다. 그러나 대부분의 콘텐츠는 개인별 추천 알고리즘 안에서 제공됩니다. 개인화 추천은 편리하지만, 친구가 어떤 콘텐츠에 관심을 갖고 어떤 관점으로 반응하는지 자연스럽게 알기는 어렵습니다.

저는 콘텐츠를 단순히 혼자 소비하는 대상이 아니라, 사람의 취향과 생각을 이해하는 대화의 출발점으로 보았습니다. 친구가 보고 있는 영상, 뉴스, SNS, 쇼핑 콘텐츠를 함께 보며 바로 반응을 나누면 링크만 주고받는 것보다 더 깊은 공감과 즐거운 경험을 만들 수 있습니다.

ViewPlus는 서로 분리된 개인화 콘텐츠 공간을 실시간으로 연결합니다. 사용자는 자신의 모바일 화면을 라이브로 공유하고, 참여자는 웹 또는 앱에서 영상을 시청하며 채팅합니다. 계정, 친구 관계, 라이브 목록, 저장 채팅을 결합해 단발성 화면 공유가 아닌 관계 기반 콘텐츠 경험을 지향합니다.

| 구분 | 내용 |
|---|---|
| 서비스 | 실시간 화면 공유, 공동 시청, 실시간 채팅, 관계 기반 라이브 |
| 송신자 | Android 사용자 1명 |
| 참여자 | 웹 브라우저 및 Android 뷰어, 현재 최대 4명 |
| 핵심 기술 | WebRTC, WebSocket, Java, Spring Boot, MySQL, Android |
| 네트워크 | Tailscale 환경 및 STUN/TURN ICE 구성 |

## 2. 사용자 경험 설계

ViewPlus의 핵심 흐름은 “누구와 함께 무엇을 볼 것인가”를 빠르게 연결하는 것입니다.

~~~text
회원가입 / 로그인
  → 친구 추가 또는 라이브 목록 탐색
  → 친구·공개 라이브 방 입장
  → 실시간 화면 공유와 채팅
  → 채팅 기록 확인 및 관계 기반 재방문
~~~

### 주요 사용자 시나리오

1. 사용자는 회원가입 후 프로필과 닉네임을 설정한다.
2. 친구를 추가하거나 공개 라이브 목록에서 흥미로운 방을 찾는다.
3. 송신자는 자신의 Android 화면을 친구 또는 전체 사용자에게 공유한다.
4. 참여자는 웹 또는 Android 앱에서 같은 화면을 보고 채팅한다.
5. 송신자는 다른 앱을 사용 중이어도 플로팅 채팅으로 메시지를 확인하고 전송한다.
6. 채팅 기록과 라이브 정보는 저장되어 이후에도 대화 맥락을 이어 갈 수 있다.

## 3. 서비스 구조

~~~text
┌────────────────────┐           WebSocket /ws          ┌──────────────────────┐
│ Android 송신 앱      │ ───────────────────────────────▶ │ Spring Boot 서버      │
│ 화면 캡처·플로팅 채팅 │ ◀─────────────────────────────── │ 인증·방·신호·채팅 API │
└─────────┬──────────┘                                  └──────────┬───────────┘
          │ WebRTC 영상                                              │
          ▼                                                          ▼
     STUN/TURN ICE                                         ┌─────────────────────┐
                                                           │ MySQL                │
                                                           │ 사용자·친구·방·채팅  │
                                                           └─────────────────────┘
          │
          └───────────────────────────▶ 웹/Android 참여자 최대 4명
                                          영상 수신·채팅·방 목록
~~~

### 역할 분리

| 계층 | 책임 |
|---|---|
| Android 송신 앱 | 화면 권한 획득, 화면 캡처, WebRTC 영상 track 생성, 플로팅 채팅 |
| 웹/Android 참여자 | 영상 수신, 라이브 목록 탐색, 채팅 참여 |
| Spring Boot | 회원 인증, 친구 관계, 방 상태, WebRTC 시그널링, 채팅 중계 |
| MySQL | 사용자, 친구 관계, 라이브 방 정보, 채팅 기록 영속 저장 |
| STUN/TURN | NAT 환경의 WebRTC 연결 지원 및 필요 시 미디어 릴레이 |

영상 자체는 WebRTC가 처리하고, 서버는 연결 신호와 서비스 데이터를 담당합니다. 이 구조는 영상 처리 부하를 Spring 서버와 분리하면서도, 계정·친구·채팅·방 목록 같은 소셜 기능을 일관된 백엔드에서 관리할 수 있게 합니다.

## 4. 핵심 도메인 설계

ViewPlus는 실시간 연결 정보와 영속 데이터의 성격이 다르므로 역할을 분리합니다.

| 도메인 | 주요 데이터 | 사용 목적 |
|---|---|---|
| User | 이메일 또는 아이디, 비밀번호 해시, 닉네임, 프로필 | 로그인과 참여자 식별 |
| UserFriend | 요청자, 대상자, 관계 상태 | 친구 요청, 수락, 차단 |
| LiveRoom | 방 제목, 송신자, 공개 범위, 상태, 시작 시각 | 라이브 목록과 입장 권한 |
| ChatMessage | 방 ID, 발신자 ID, 메시지, 생성 시각, 삭제 상태 | 실시간 채팅과 이전 기록 |
| WebSocketSession | clientId, 현재 roomId | 접속 중인 사용자와 시그널링 관리 |

MySQL에는 사용자·친구·방·채팅처럼 재접속 후에도 남아야 하는 정보를 저장합니다. 반면 WebSocketSession과 ICE candidate처럼 짧은 시간만 필요한 연결 정보는 메모리에서 관리합니다.

## 5. 실시간 화면 공유 기술

### WebRTC와 시그널링 분리

화면 영상은 낮은 지연 시간이 필요한 WebRTC로 전송하고, Spring WebSocket은 WebRTC 연결을 시작하기 위한 시그널링을 담당합니다.

~~~text
송신자                  Spring 서버                  참여자
  │ join publisher          │                            │
  │────────────────────────▶│◀───────────────────────────│ join viewer
  │◀─────────────────────── peer-ready ────────────────▶│
  │ offer(targetId)         │                            │
  │────────────────────────▶│───────────────────────────▶│
  │◀─────────────────────── answer(targetId) ───────────│
  │◀───────────────────── ICE candidate 교환 ──────────▶│
  │=================== WebRTC 영상 연결 =================│
~~~

송신자 한 명에게 여러 참여자가 연결될 수 있으므로 offer, answer, candidate에는 targetId를 포함합니다. 이를 통해 각 참여자별 PeerConnection을 구분합니다.

### 다중 뷰어 구조

현재 MVP는 송신자 1명과 최대 4명 참여자의 소규모 mesh 구조입니다.

~~~text
ScreenCapturerAndroid
        │
    VideoTrack 1개
   ┌────┼────┐
   ▼    ▼    ▼
viewer A  viewer B  viewer C
~~~

한 개의 화면 VideoTrack을 각 뷰어 PeerConnection에 연결합니다. 새 참여자가 입장하면 기존 화면 track을 재사용해 해당 참여자에게만 새 offer를 보냅니다.

소규모 공동 시청에는 단순하고 이해하기 쉬운 구조이지만, 시청자가 많아지면 송신 휴대폰의 업로드 대역폭 부담이 커집니다. 향후 다수 시청자 환경에서는 SFU 기반 미디어 서버를 검토합니다.

### NAT 환경 대응

STUN과 TURN ICE 서버 설정을 Android와 브라우저에 전달합니다.

- STUN으로 직접 연결을 우선 시도
- 직접 연결이 어려운 환경은 TURN relay 후보 사용
- relay candidate와 ICE CONNECTED 로그로 연결 상태 검증

## 6. Android 화면 공유와 사용성

Android 앱은 MediaProjection API로 화면을 캡처하고, WebRTC VideoTrack으로 전송합니다.

Android 14 이상에서는 화면 캡처 전에 mediaProjection 타입 foreground service가 준비돼 있어야 합니다. 이를 지키기 위해 다음 흐름을 구현했습니다.

~~~text
화면 공유 요청
  → Android 화면 캡처 권한
  → ScreenCaptureService 시작
  → startForeground 완료
  → 준비 broadcast
  → ScreenCapturerAndroid 시작
  → VideoTrack 생성 및 offer 전송
~~~

이 순서로 foreground service 준비 전 캡처가 실행되어 발생하는 SecurityException을 해결했습니다. 캡처가 실패하면 빈 영상 track으로 WebRTC 협상을 보내지 않도록 방어했습니다.

### 플로팅 채팅

송신자는 화면 공유 중에도 다른 앱을 사용할 수 있습니다. 이를 고려해 다른 앱 위에 표시 권한과 WindowManager overlay를 이용한 플로팅 채팅을 구현했습니다.

- 기본 상태는 작은 채팅 버튼
- 버튼을 누르면 최근 메시지와 입력창 표시
- 다시 누르면 접힘
- 새 메시지 도착 표시
- 플로팅 창에서 바로 채팅 전송

이는 화면을 공유하는 사용자가 콘텐츠 소비를 멈추지 않고 대화에 참여하도록 만든 UX입니다.

## 7. 인증, 친구, 라이브 발견

실시간 기능이 지속적인 서비스 경험으로 이어지려면 사용자를 식별하고 관계를 관리해야 합니다. 이에 따라 MySQL과 Spring Security를 기반으로 다음 기능을 설계·구현할 예정입니다.

### 회원가입과 로그인

- 이메일 또는 아이디 기반 회원가입
- BCrypt를 사용한 비밀번호 해싱
- Spring Security 기반 인증
- 세션 또는 토큰 기반 로그인 유지
- 프로필, 닉네임, 공개 범위 설정

비밀번호 원문은 어떤 경우에도 저장하지 않습니다. TURN 자격 증명 같은 민감한 설정도 코드 저장소가 아닌 환경 변수 또는 Secret Manager로 분리합니다.

### 친구 관계

친구 목록은 신뢰하는 사람의 라이브를 발견하고 함께 보기 위한 기능입니다.

- 친구 요청, 수락, 거절, 차단
- 친구의 온라인 상태와 라이브 시작 여부
- 친구 공개 라이브 방과 초대
- 친구별 라이브 알림 설정

### 실시간 라이브 방 목록

방 이름을 알고 있어야만 입장할 수 있는 초기 구조를 개선해, 사용자가 현재 진행 중인 라이브를 발견할 수 있는 목록을 제공합니다.

| 정보 | 목적 |
|---|---|
| 방 제목 | 콘텐츠 주제 파악 |
| 송신자 프로필 | 누구의 라이브인지 식별 |
| 시청자 수 | 참여 상태 확인 |
| 공개 범위 | 전체, 친구, 비공개 구분 |
| 시작 시각 | 라이브 최신성 판단 |

방 입장·퇴장·종료 이벤트는 WebSocket으로 반영해 목록을 실시간으로 갱신합니다.

## 8. 저장 채팅과 실시간 채팅의 결합

채팅은 실시간 대화와 이후 재방문 경험을 동시에 만족해야 합니다.

~~~text
클라이언트 채팅 전송
  → Spring WebSocket Handler
  → ChatMessage MySQL 저장
  → 같은 방 참여자에게 실시간 broadcast
  → 새 참여자는 최근 채팅 기록 조회
~~~

채팅 메시지는 메시지 ID, 방 ID, 발신자 ID, 내용, 생성 시각, 삭제 상태를 저장합니다. 보낸 사람에게는 서버 응답을 기다리지 않고 즉시 표시하는 낙관적 UI를 적용하고, 이후 메시지 전송 실패 또는 재시도 기능까지 확장할 수 있습니다.

## 9. UI/UX 방향

영상이 중심이 되도록 Android와 웹에 공통 디자인 원칙을 적용했습니다.

- 영상 위에 겹치는 반투명 glass 스타일 패널
- 상단: 방 이름, 공유, 보기 동작
- 하단: 접기와 펼치기가 가능한 실시간 채팅
- 웹: 반응형 영상 영역과 채팅 오버레이
- Android: 다른 앱 위에서도 확인 가능한 플로팅 채팅
- 향후: 친구 목록, 라이브 목록, 알림, 프로필 설정 화면

사용자는 복잡한 설정 없이 라이브 목록에서 방을 찾고, 입장 후에는 영상과 대화에 집중할 수 있어야 합니다.

## 10. 트러블슈팅 사례

### 문제

ICE 상태가 CONNECTED 또는 COMPLETED인데도 뷰어가 검은 화면을 보며 frames received 값이 0인 상황이 발생했습니다.

### 원인 분석

1. TURN relay candidate 생성 여부 확인
2. ICE 상태 전이 확인
3. renderer 수신 프레임 수 확인
4. Android 캡처 로그 확인
5. foreground service 관련 MediaProjection 보안 예외 확인

### 해결

foreground service가 준비된 뒤에만 화면 캡처를 시작하도록 순서를 수정하고, 캡처 실패 시 빈 영상 협상을 막았습니다.

### 학습 결과

WebRTC는 ICE 연결 성공만으로 영상 전송 성공을 판단할 수 없습니다. 권한, 캡처, track 생성, SDP 협상, ICE, 원격 track, renderer 프레임까지 단계별 관측이 필요하다는 점을 경험했습니다.

## 11. 기술 의사결정

| 선택 | 이유 | 트레이드오프 |
|---|---|---|
| WebRTC | 낮은 지연 시간 화면 전송 | SDP와 ICE 상태 관리 필요 |
| Spring WebSocket | 인증, 방, 시그널링, 채팅 통합 관리 | 다중 서버에서는 세션 공유 필요 |
| MySQL | 사용자와 관계, 채팅 기록의 영속성 | 스키마와 인덱스 설계 필요 |
| Mesh fan-out | 소규모 공동 시청에서 구현이 단순 | 뷰어 증가 시 송신자 대역폭 부담 |
| TURN | NAT 환경 연결 성공률 개선 | 릴레이 비용과 서버 관리 필요 |
| WebSocket 채팅 | 웹·Android 공통 구현이 단순 | 읽음 상태와 재전송은 추가 설계 필요 |
| Android overlay | 다른 앱 사용 중에도 대화 유지 | 별도 사용자 권한과 lifecycle 관리 필요 |

## 12. 구현 상태와 다음 단계

현재 구현된 MVP는 WebRTC 화면 공유, 최대 3명 뷰어 연결, WebSocket 시그널링, 웹·Android 실시간 채팅, Android foreground service, 플로팅 채팅입니다.

다음 개발 단계는 MySQL 기반 회원, 로그인, 친구 관계, 저장 채팅, 실시간 라이브 목록을 도입해 기술 검증용 화면 공유 앱을 관계 기반 소셜 라이브 서비스로 확장하는 것입니다.

추가로 진행할 기술 과제는 다음과 같습니다.

1. Spring Security와 MySQL 기반 인증 구현
2. User, Friend, LiveRoom, ChatMessage 엔티티 및 API 설계
3. WebSocket 메시지 DTO와 입력 검증 강화
4. Redis를 이용한 다중 Spring 서버 방 상태 공유
5. 화면 공유 종료와 foreground service 정리 흐름 추가
6. 대규모 시청 환경의 SFU 도입 검토
